# R9 — real mobile-touch and TLS-terminated HTTPS/WSS acceptance

Draft, stacked on R8 actual Chrome/Edge browser acceptance PR #48. No login, no host-approval entrance, and unchanged member/token game permissions.

## Implementation

- Extend `server/game-room-browser-e2e.mjs` to use **Chrome DevTools `Input.dispatchTouchEvent`** with device metrics set to **390 × 844** and touch emulation enabled. Unlike manually constructing `PointerEvent`, this drives the browser's actual touch-to-pointer event conversion and native `touch-action` behavior.
- Launch a disposable **loopback HTTPS reverse proxy** in Node, with a temporary self-signed PKCS12 certificate generated by the already-installed JDK `keytool`. It sends HTTP and bearer writes to the real GameCenter client HTTP listener; it forwards RFC 6455 upgrade frames to the actual plaintext WebSocket server. The browser connects to **`https://` and `wss://`** (not simulated URL parsing).
- The headless test browser only is started with `--ignore-certificate-errors` to accept this **throwaway local** certificate. No certificate/key file is committed and no globally trusted certificate is installed. Do not use this bypass or self-signed setup in a real deployment.
- Fix `GameClientHttpServer.resolvedWebSocketUrl`: if the request passes through a **trusted loopback HTTPS reverse proxy** and no explicit `publicWebSocketUrl` is configured, use the frontend's WSS origin/port, not the **internal plaintext WebSocket** listener's port. Explicit `publicWebSocketUrl` remains authoritative for deployments that expose a distinct external WS endpoint. Plain HTTP + WS direct mode unchanged.

## Real-browser gates

1. Create the public Drawing Guess room through its existing production UI over TLS, without a registered account, and join from another browser context as SPECTATOR.
2. Confirm the browser receives `wss://<public host>:<TLS proxy port>/` via `/api/client/config` and establishes member-authenticated WebSocket replay after a real TLS upgrade.
3. Set up a **STREAMER_DRAWER** game with a single host player, mark ready and start a round using the production answer form. Touch-draw across the actual Canvas with five CDP touch samples.
4. The remote spectator must receive and render the resulting authoritative Canvas line (nonwhite pixel in the stroke path) via **WSS**, not just receive a Java test event.
5. Drawing must not scroll the page under the moving finger; the 390px layout must not have horizontal overflow.
6. Kick the spectator over HTTPS. The authenticated WSS room subscription must close with **1008** and the old member bearer must fail over the same TLS proxy.
7. Existing R8 two-browser real HTTP/WS tests, R1–R7 Java regression probes, browser JS checks and Windows package remain mandatory.

## Scope and limitations

This exercises a real TLS socket, a real Chromium engine, real touch event dispatch, same-origin HTTP and upgraded WebSocket framing on a local Windows GitHub runner. It does **not** prove publicly issued certificate trust, production reverse-proxy configuration, WAN routing, Safari/iOS/Android hardware multitouch, or real mobile browser performance. Those still require a deployed/staged endpoint and device matrix.

Reverse-proxy hardening: the backend trusts `X-Forwarded-*` only when the peer connects from loopback. TLS should terminate in a controlled local proxy and the application must not expose an untrusted public local-forward tunnel as a proxy. Production should configure `publicBaseUrl` and `publicWebSocketUrl` explicitly when using a different public hostname/path/port.
