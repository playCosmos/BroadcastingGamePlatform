# GameRoom R2 — 회원 자격·초대·방장 권한

> 상태: 서버 내부 인증 서비스 + HTTP 경계 구현. [R1](./GAME_ROOM_R1.md)과 [공통 룸 개발 계획 PR #36](https://github.com/playCosmos/BroadcastingGamePlatform/pull/36) 참조.
>
> R2는 Draft #38 (R1 #37 위에 스택됨). 게임별 플레이어 턴 권한과 실제 게임 클라이언트는 R4/R5, 채팅·presence WebSocket은 R3에서 적용한다.

## 신원 및 비밀

- 방장을 포함한 모든 회원은 서버가 발급하는 256-bit 난수 비밀 자격을 가지며, DB에는 SHA-256 해시만 저장한다.
- 관리자 세션 쿠키는 룸 개설을 위해서만 사용한다. **회원 Bearer 토큰은 관리자 세션이 아니며 관리자 API 권한을 발급하지 않는다.**
- 초대권 토큰과 회원 토큰을 서로 다른 테이블/수명주기로 관리한다. 방 코드를 알아도 룸 입장/관리/게임 플레이 권한은 없다.
- 초대권 소모/정원 검사/회원 생성/회원 토큰 발급, 방장 룸 개설/호스트 자격 발급은 각각 **같은 SQLite BEGIN IMMEDIATE 트랜잭션**에서 커밋한다.
- 회원의 실제 actor ID와 저장된 credential hash는 공개 룸 JSON에서 제외한다. 내부 `Room` 모델은 HTTP에 직접 직렬화하지 않는다.
- 회원 세션 유효기간은 임시값 7일, 초대권 유효기간은 7일 이내, 초대권 최대 사용 횟수는 256회로 기술적으로 제한한다. 제품 기본값으로 승인된 수치가 아니다.
- 세션을 명시적으로 회전할 때 원본은 즉시 폐기하며, 퇴장·강퇴 시 회원 세션을 모두 폐기한다.

## 권한 규칙

| 기능 | 관리자 세션 | 현 방장 토큰 | 일반 플레이어 토큰 | 관전자 토큰 |
| --- | --- | --- | --- | --- |
| 룸 생성(방장 최초 토큰 발급) | 예 | 아니오 | 아니오 | 아니오 |
| 룸 회원 조회 | 회원 토큰 별도 필요 | 예 | 예 | 예 |
| 초대권 생성/회수 | 아니오 | 예 | 아니오 | 아니오 |
| 다른 회원 방장 위임 | 아니오 | 예 | 아니오 | 아니오 |
| 강퇴·차단 / 정원 변경 | 아니오 | 예 | 아니오 | 아니오 |
| 자신의 좌석 변경 | 회원 자격 필요 | 예 | 예 | 예 |
| 자신 준비 완료 | 회원 자격 필요 | PLAYER인 경우 | 예 | 아니오 |
| 재접속/로그아웃/토큰 회전 | 회원 자격 필요 | 예 | 예 | 예 |

- 방장 위임은 저장된 `owner_member_id`만 변경한다. 기존 방장 토큰은 여전히 자신의 회원 토큰이지만 **관리 권한은 즉시 사라진다**.
- 강퇴는 회원을 `KICKED`로 전환하고 모든 현 세션을 폐기하며 actor ID에 차단 기록을 남긴다.
- **주의:** 게스트가 완전히 새로운 비연결 익명 정체성을 발급받으면 동일인임을 증명할 수 없으므로, R2 차단은 기존 멤버십·자격에 대한 실효성만 보장한다. 영구적인 사람/기기 차단이라는 잘못된 약속을 하지 않는다. 추후 연결된 플랫폼 계정·확인된 신원 정책이 결정돼야 한다.
- 활성 게임 도중 플레이어 강퇴/퇴장은 금지한다. 실제 게임 턴·그림·점수에 영향 주는 예외 처리는 R4/R5 모드별 정책이다.
- 잠시 연결이 해제된 방장은 관리 명령 불가. 유효 자격으로 허용 시간 내 다시 연결 후 관리 기능을 복원한다.
- 초대권 발급과 좌석 부족은 다른 경계다: 플레이어/전체 정원 검사는 **초대권 실제 사용 시점**에 실행한다.

## HTTP 엔드포인트

`/api/v1/room-membership` 루트 아래에서 다음을 제공한다. 쓰기 작업은 요청 `Origin`이 서버의 공인 원본과 일치해야 하며, 일반 회원은 `Authorization: Bearer <43-character secret>`으로 인증한다.

| HTTP | 경로 | 자격 |
| --- | --- | --- |
| POST | `/hosted` | 관리자 인증 쿠키 + Origin, 지원 게임 Yacht(2~6)/Drawing Guess(1~20)의 정원 |
| POST | `/join` | 유효하고 미사용/미만료된 초대권 + Origin + 빈도 제한 |
| GET | `/me` | 룸 회원 Bearer |
| POST | `/me/ready`, `/me/seat`, `/me/leave` | 룸 회원 Bearer + Origin |
| POST | `/me/disconnect`, `/me/reconnect` | 룸 회원 Bearer + Origin |
| POST | `/me/rotate`, `/me/logout` | 룸 회원 Bearer + Origin |
| POST | `/host/invite`, `/host/revoke-invite` | 현재 방장 Bearer + Origin |
| POST | `/host/transfer`, `/host/kick`, `/host/capacity` | 현재 방장 Bearer + Origin |

모든 쓰기 JSON 요청은 작은 크기 제한(8KiB)과 허용 필드 검사로 처리한다. 클라이언트가 직접 actor ID, 관리자 세션, 주사위, 출제자 비밀을 선택할 수 없다.

실제 게임 플레이는 **아직 이 HTTP API에 연결되지 않았으며**, R4/R5에서 회원 identity와 현재 턴 권한을 게임별 authority에 바인딩한다. 공통 룸의 참가자와 기존 Yacht Y2 게임 참가자가 같은 사람이 되는 것은 자동이 아니다.

## 통합·검증 기준

- `GameRoomR2Probe`: DB 실연결 기반 7일 회원 자격, 유한 초대권, 유효/만료/회수, 방장 위임 즉시 권한 변동, 강퇴/토큰 폐기, 재시작 복구, 마지막 자리에 16개 초대 요청 경쟁 성공 1건 검증.
- `GameRoomHttpR2Probe`: 기존 AdminAuthStore가 실제 발급한 쿠키/Origin을 사용해 룸 생성, 초대, 입장, 일반 회원 준비/접근 통제, 방장 승계, 강퇴 및 공개 응답 개인정보 제외 확인.
- R1 인원 불변식, Yacht Y0–Y2, Board·Drawing Guess 기존 회귀 모두 유지.
- R3에서는 공통 룸 채팅/WS Presence를 추가하되 현재 멤버십 인증을 그대로 재사용하고, 이미 만료/회수된 토큰을 WS 연결의 재연결 자격으로 인정하지 않는다.
- R2에서 추가한 세션/초대/차단 저장소는 별도 마이그레이션 `V32`. 병합 순서가 달라질 경우 마이그레이션 번호·DB 백업 검증을 재확인한다.
